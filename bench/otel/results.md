# otel adapter benchmark

Run on 2026-09-24 with `jev-1.13.0`, 6 synthetic incidents (`bench/otel/`, generated by `make_data.py`), 3 runs per task and arm. Each incident is a 30-minute OTLP JSON log export from six services, about 1,400 records.

| Arm | Accuracy | Median input tokens | Median latency (ms) | Median confidence | Median options |
|---|---|---|---|---|---|
| raw | 83% (15/18) | 29678 | 2346 | 0.90 | 254 |
| jevbrief | 100% (18/18) | 1070 | 2128 | 1.00 | 5 |

| Incident | raw | jevbrief |
|---|---|---|
| Checkout requests started failing with 500 errors | 3/3 | 3/3 |
| Users cannot log in anymore | 3/3 | 3/3 |
| Product pages are very slow and some time out | 3/3 | 3/3 |
| Customers say they are not getting order confirmation emails | 3/3 | 3/3 |
| Every request returns 502 since the last deploy | 0/3 | 3/3 |
| Orders fail with an out of stock error even though items are in stock | 3/3 | 3/3 |

## Notes

- **Raw arm:** the 254 most recent raw log lines (the Choice option limit), each with its service, severity, and ISO timestamp. This is what a naive "send the latest logs" integration looks like, and it sits close to Jev's 32k-token context limit.
- **jevbrief arm:** log groups with severity, frequency, first-seen, and still-happening computed in code; info and debug noise and health checks dropped.
- The raw arm's only misses are the deploy incident: the cause is a single config error logged once, 20 minutes before the export ends, so it had scrolled out of the most recent 254 lines. This is by design of the task and is the typical failure of recent-lines integrations.
- A task is correct when the chosen group or line contains the root cause text (`expected_contains`).
- The incidents are synthetic and were written while building the adapter, so the rules (for example, boosting groups that start at the incident start) were designed with this kind of data in mind. Treat the numbers as an illustration, and please contribute real, anonymized incident exports.
