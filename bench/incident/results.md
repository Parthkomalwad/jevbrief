# otel incident pack benchmark

Run on 2026-09-26 with `jev-1.13.0`, 8 synthetic incidents (`bench/incident/`, generated by `make_data.py`), 3 runs per task and arm. Each incident is a folder with a 30-minute OTLP log export (about 1,400 records from six services), `kubectl get events -o json` output (about 20 events), and Alertmanager `/api/v2/alerts` output (4 to 5 alerts).

**Question:** which signal (a log group, a group of Kubernetes events, or an alert) most likely shows the cause of the incident? **Right answer:** the chosen signal contains the root cause text (`expected_contains`).

| Arm | Accuracy | Median input tokens | Median latency (ms) | Median confidence | Median options |
|---|---|---|---|---|---|
| raw | 71% (17/24) | 29912 | 542 | 0.65 | 254 |
| jevbrief | 100% (24/24) | 1830 | 316 | 0.99 | 8 |

| Incident (cause in) | raw | jevbrief |
|---|---|---|
| oom_checkout: Checkout keeps failing with 503 errors | 3/3 | 3/3 |
| image_pull: Payments are failing since the release w | 3/3 | 3/3 |
| cert_alert: Nobody can log in | 3/3 | 3/3 |
| disk_pressure: Product pages are timing out | 0/3 | 3/3 |
| coredns_crash: Most requests are failing across the sit | 3/3 | 3/3 |
| quota: Orders are very slow under the evening l | 2/3 | 3/3 |
| pool_logs: Checkout requests started failing with 5 | 3/3 | 3/3 |
| config_log: Every request returns 502 since a few mi | 0/3 | 3/3 |

Where the cause is: oom_checkout, image_pull, disk_pressure, coredns_crash, and quota in Kubernetes events; cert_alert in an alert; pool_logs and config_log in the logs.

## Notes

- **Synthetic, and written by the same person as the rules.** The incidents were written while extending the adapter, so treat the numbers as an illustration, not evidence. Please contribute real, anonymized incident exports.
- **Labels were fixed before the run.** The generator and `tasks.json` were committed (e5dc6c1) before any call to Jev and not changed after.
- **Raw arm:** every Kubernetes event and alert (there are few), then the most recent raw log lines, up to 254 items (the Choice option limit). Sending every event and alert is what a naive integration would do, and it is kinder to the raw arm than sending only the most recent records, which would miss most of the causes.
- **jevbrief arm:** signal groups with severity, frequency, first-seen, still-happening, and alert state computed in code. Routine events (Scheduled, Pulled, Created, Started), an alert that resolved before the incident, info and debug noise, and log health checks are dropped. A median of 8 signals reach Jev.
- **Why the raw arm missed:**
  - disk_pressure (0/3) and quota (1 of 3 runs): it chose a background "slow query" warning that repeats through the whole export.
  - config_log (0/3): the cause is a single log line that had scrolled out of the most recent lines. The same weakness as the otel deploy incident. This task favours jevbrief by design.
- **Confidence:** even where the raw arm was right, Jev was often unsure: a median of 0.65, with several right answers at 0.46 to 0.52. At the default `min_confidence` of 0.5, some of those would have been `low_confidence` and taken no action. jevbrief's median confidence was 0.99.
- **A known weakness:** alerts do not set the incident start, because alerts fire after the cause. In cert_alert the only cause signal is an alert, so the start comes from the first symptom logs and the cause alert reads as "before the incident". Jev still picked it every time.
- **Small set.** 8 incidents, one of each kind. A real cluster run with injected faults (for example, the OpenTelemetry demo's fault flags) is the next step.
